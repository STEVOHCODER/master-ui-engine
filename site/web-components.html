Documentation · Web Components

43 custom elements that use your stylesheet instead of their own.

The mue-* elements are plain ES modules with no shadow roots. They add markup and behaviour inside your document, so styles/components.css, the design tokens and the html.dark flip reach them without ::part or adoptedStyleSheets plumbing. One <script type="module"> registers every tag. Nothing is hosted, nothing is published to npm, and nothing needs a build.

Load them four ways

Pick the one that matches the project you already have. The first needs no tooling at all, which is the point of this port.

a page that renders
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  --> <link rel=stylesheet href="design-tokens/engine.css">
  <link rel=stylesheet href="styles/components.css">
  <script src="styles/mue.js" defer></script>
  --> <script type="module" src="frameworks/web-components/index.js"></script>
</head>
<body class="page">
  <mue-button variant="primary">Save changes</mue-button>
  <mue-input label="Email" type="email" name="email"
            helper="Never shared with third parties."></mue-input>
  <mue-card variant="elevated">
    <div class="card-body">…</div>
  </mue-card>
</body>
</html>

// the two stylesheets are still yours to import

local install

works, but reads the folder in place.

The file: install is the weakest of the four: it registers mue-web-components as a link to the folder inside the checkout rather than a copy, so deleting or moving the repository breaks the import. It is also not a published package — npm i mue-web-components will fail, because nothing has been published. The CLI page explains why this project installs files instead of resolving a registry.

What an element actually renders

Dumped from the browser after the modules registered, not written by hand. This is the contract: the host builds real child nodes out of the classes in styles/components.css, and the theme sheet sees them because they are in the document.

outerHTML, three elements
<mue-button variant="primary"><button type="button" class="btn-primary">Save changes</button></mue-button>

<mue-input label="Email" type="email" name="email" helper="…"><div class="field">
  <label class="field-label" for="mue-input-1">Email</label>
  <input id="mue-input-1" type="email" placeholder="" name="email">
  <p class="field-helper" id="mue-input-1-helper">Never shared with third parties.</p>
</div></mue-input>

<mue-card variant="elevated" class="card card-elevated">…</mue-card>
No shadow rootEvery host in the suite reports shadowRoot === null. That is a design decision, not a gap — frameworks/web-components/README.md documents it under “Why light DOM”.
The host is the componentmue-card gains class="card card-elevated" on itself rather than wrapping your children in a div, so your own classes sit beside the ones it adds.
Real form controlsmue-button renders a <button type="button">; mue-input renders an <input> whose id is bound to a <label for>, so keyboard focus, form submission and a screen reader’s accessible name all come from HTML rather than from ARIA emulation.
The costBecause the host rebuilds its children, the child markup per element is fixed and documented. You cannot nest arbitrary content inside mue-button and expect it to survive — the gallery shows what each element accepts.

The 11 events

Every event is a CustomEvent that bubbles from the host, so one listener on a container is enough. Names are prefixed because a bare change would collide with the native event on the <input> inside.

mue-changeThe value changed — inputs, textareas, selects, checkboxes, radios, switches, rating, progress, tabs, date picker, dropzone. Carries the new value in event.detail.
mue-open · mue-closeOverlay lifecycle for mue-dialog, mue-modals, mue-popover, mue-dropdown, and mue-notification / mue-fab / mue-guidance on the close side.
mue-selectAn option was chosen — mue-dropdown, mue-nav-menu, mue-datatable row selection.
mue-navigateA link inside a navigation element was activated: mue-header-nav, mue-nav-menu and the three sidebar tags.
mue-sort · mue-filter · mue-expandTable interactions owned by mue-datatable — column sort, query filter, row disclosure.
mue-page-changePagination moved, with the new page on mue-pagination.
mue-removeA file was taken out of the mue-dropzone list.
mue-stepThe active step changed on mue-stepper, and on the mue-guidance and mue-fab tour controls.

What this page does not claim

!

Not published to npm

mue-web-components is the name the folder would ship under; it is not on the registry. Installation is a file copy from a git checkout, described on the CLI page. Publishing is on the roadmap in README.md and has not happened.

!

No framework interop verified

The React and Vue ports are independent implementations of the same tokens and component classes, written separately. They do not wrap these elements and these elements do not wrap them. No mixed-framework project has been built or tested, so nothing here promises that a React app can mount <mue-card> and keep its props in sync.

!

Never run on some engines

Chrome and Edge only. Not run: Safari, Firefox, a screen reader, a real touch device, server-side rendering, and a published-package install. Custom elements and form-associated behaviour differ across engines, so a Safari result is genuinely unknown rather than assumed good.

!

Light DOM is a trade, not a win

Your document stylesheet reaches the elements — that is the benefit. The price is that document-level CSS also reaches into them, and the host rebuilds its children, so a global button { } rule can override btn-primary. The gallery is the reference for which markup each element expects.
